## 1. The 60-second answer

**You asked: what runs client-side prediction, and what runs the server simulation?**

| Concern | File | Function |
|---|---|---|
| **The simulation rules themselves** (shared, authoritative logic) | `engine/src/Simulation.cpp` | `processPlayerInput()`, `updateWorld()` |
| **The server** (owns truth, runs 60 Hz, broadcasts snapshots) | `game/src/Server.cpp` | `runServer()` |
| **The client prediction + reconciliation** | `game/src/PlayingState.cpp` | `PlayingState::update()` |
| **The wire layer on the client** (send input, receive snapshots, interpolate) | `game/src/NetworkClient.cpp` | `sendCommand()`, `poll()`, `getInterpolatedPlayer()` |
| **The packet formats** | `engine/include/Snapshot.h` | `Snapshot`, `CommandPacket`, `WelcomeMessage` |

The crucial nuance, and the thing `development_notes.md` gets *slightly* wrong:

> `development_notes.md` says "Simulation.cpp is the server-side simulation, PlayingState.cpp is the client-side simulation."

More precisely: **`Simulation.cpp` is the *shared* simulation code, compiled into both.**
The server calls it as the authority; the client calls the *exact same functions* to
predict locally and to replay unacknowledged inputs during reconciliation. That shared-code
property is the whole reason the prediction is able to agree with the server at all.

`PlayingState.cpp` is not a separate simulation — it is the **client-side driver** of
`Simulation.cpp`, plus all rendering, plus input sampling, plus the reconciliation loop.

**Two important consequences of how it's currently wired** (both detailed in §14):
- The client **never calls `updateWorld()`**, so world entities, round/match phase logic
  and entity physics exist *only* on the server. The client renders entities purely from
  the snapshot.
- The client's `PlayerState::weapon` and `::ability` are **always `nullptr`**, because
  `giveRoundItems()` is only ever called from `Server.cpp`. So item effects are never
  predicted.

## 2. Build, run, and project layout

### `CMakeLists.txt`

C++17, exports `compile_commands.json` (for clangd — hence the `.cache/clangd/` directory).

Three build targets:

| Target | Type | Contents |
|---|---|---|
| `glad` | static lib | `vendor/glad/src/glad.c`, publicly exposes `vendor/glad/include` |
| `engine` | static lib (`libengine.a`) | 10 `.cpp` from `engine/src/`; publicly exposes `engine/include` **and `vendor/`**; links `glad` publicly |
| `game` | executable | 11 `.cpp` from `game/src/`; links `engine glfw OpenGL::GL glm::glm enet` privately |

System packages found via `find_package`: `glfw3`, `glm`, `OpenGL`. There is a
`find_package(unofficial-enet CONFIG QUIET)` line, but the actual link is the bare name
`enet` — so on this machine ENet resolves as a plain system library, not through the
CMake config package. (This is why the `QUIET` find can fail harmlessly.)

**Note:** `engine` publicly exposes `vendor/`, which is how `nlohmann/json.hpp` and
`stb/stb_image.h` become includable from anywhere that links `engine`.

**Note:** the engine library does **not** link glfw or glm directly; it gets glm through
transitive includes and `Camera.cpp` includes `<GLFW/glfw3.h>` relying on the include path
being globally available. This works but is fragile.

### Vendored dependencies (`vendor/`, gitignored)

- `glad` — OpenGL 3.3 core function loader.
- `stb/stb_image.h` — image decoding, implementation compiled in `Texture.cpp`.
- `nlohmann/json.hpp` — JSON parsing, used only by `Level.cpp`.

`.gitignore` excludes `build/`, `*~`, and `vendor/`. The gitignore carries a note that
`vendor/` should be purged from the GitHub repo history once README build instructions exist.

```sh
./run.sh          # builds, cd game/src, runs ../../build/game        → CLIENT
./run_server.sh   # builds, cd game/src, runs ../../build/game --server → SERVER
```

**The single binary is both.** `main.cpp:76` checks `argv[1] == "--server"`; if so it calls
`runServer()` and returns *before* any GLFW/GLAD initialisation. The server is headless and
never opens a window or touches OpenGL.

### The three layers of state

There are three distinct representations of the game world. Knowing which is which is the
key to reading the netcode:

| Layer | Type | Where | Contains pointers? | Purpose |
|---|---|---|---|---|
| **Authoritative state** | `GameState` | server memory (`Server.cpp:29`) | yes (`Item*`, `WorldEntity*`) | the truth |
| **Wire state** | `Snapshot` | inside UDP packets | **no** — POD only | transport |
| **Predicted state** | `GameState` | client memory (`PlayingState` member) | yes, but item pointers are **null** | what you see |

`learning/netcode.md` records exactly why the split exists: *"we cant send GameState over
packets bc it has pointers which will mean nothing on other computers, and things like
vectors which isnt fixed size. So we have snapshot.h which is a packet safe version."*

## 4. The netcode, in full

This is the chapter to read first. Everything here is verified against the code.

### 4.1 Transport

ENet over UDP, port **7777**, 2 channels allocated but **only channel 0 is ever used**.

- **Server** (`Server.cpp:21`): `enet_host_create(&myAddress, 32, 2, 0, 0)` — binds
  `ENET_HOST_ANY:7777`, up to 32 peers, 2 channels, no bandwidth caps.
- **Client** (`NetworkClient.cpp:6`): `enet_host_create(nullptr, 1, 2, 0, 0)` — `nullptr`
  address = don't bind/listen, 1 outgoing peer slot.

`enet_initialize()` is called once in `main()` (`main.cpp:78`) for both roles.

### 4.2 Message framing

Every packet the **server sends** is prefixed with a 1-byte `MessageType`
(`Snapshot.h:38-42`):

```
Server → Client:   [ 1 byte type ][ payload ]
                     0 = Snapshot   sizeof(Snapshot)
                     1 = Welcome    sizeof(WelcomeMessage)
```

Packets the **client sends** have **no type byte at all**. The server identifies them
purely by size (`Server.cpp:96`):

```
Client → Server:   [ sizeof(CommandPacket) bytes, raw ]
```

`if (event.packet->dataLength == sizeof(CommandPacket))`. Any packet of a different size
is silently dropped. This asymmetry is a latent problem the moment you add a second
client→server message type — you will have to add a type byte and update the check.

All payloads are transferred by raw `memcpy` of the struct. There is **no serialisation,
no byte-order conversion, no struct packing directive, and no protocol version field.**
This is fine for localhost / same-compiler testing and will break across differing
architectures or compiler ABI settings.

### 4.3 Reliability flags

| Packet | Direction | Flag | Reasoning |
|---|---|---|---|
| `Welcome` | S→C | `ENET_PACKET_FLAG_RELIABLE` (`Server.cpp:87`) | you *must* learn your player index |
| `Snapshot` | S→C | `0` = unreliable (`Server.cpp:239`) | correct — a lost snapshot is superseded 16 ms later |
| `CommandPacket` | C→S | `0` = unreliable (`NetworkClient.cpp:59`) | correct — loss is covered by redundancy (§4.4) |

`Snapshot` is broadcast to *all* peers with `enet_host_broadcast` (`Server.cpp:240`), not
sent per-peer. Every client receives the full state of both players. (No fog-of-war /
relevancy filtering — irrelevant for a 1v1 shooter, but note it means the snapshot is not
per-client tailored.)

### 4.4 Client → Server: input commands

**`InputCommand`** (`engine/include/InputCommand.h`) is the unit of player intent. It is
pure intent — no positions, no results:

```
sequence            unsigned int   0 means "empty slot"
moveForward/Back/Left/Right, jump  bool
lookDirection       glm::vec3      full 3D aim vector, not yaw/pitch
equipWeapon, equipAbility          bool
primaryPressed / primaryHeld       bool  (edge vs level)
secondaryPressed / secondaryHeld   bool
dash                bool  (edge triggered)
crouch              bool
```

Note `lookDirection` is sent as a full `vec3` (12 bytes) rather than two angles. That's
generous bandwidth-wise but means the client's aim is trusted verbatim — the server
assigns it straight into `player.lookDirection` at `Simulation.cpp:33` with no validation
or normalisation. An aimbot/spoofed client is entirely unconstrained here.

**Sampling** happens at a fixed 60 Hz inside `PlayingState::update()`'s accumulator loop
(`PlayingState.cpp:149-200`), *not* per render frame. Keyboard is polled with
`glfwGetKey`, mouse buttons with `glfwGetMouseButton`. Edge-triggered inputs
(`primaryPressed`, `secondaryPressed`, `dash`) are derived by comparing against
`primaryWasDown` / `secondaryWasDown` / `dashWasDown` members.

**A subtlety about edge detection:** those `*WasDown` flags are updated inside the
*tick* loop, not the *frame* loop. If a frame takes longer than 2 ticks, the accumulator
runs the loop twice and the second iteration sees `WasDown == true` — so a click can only
ever produce one `Pressed` edge per burst. That is the correct behaviour, but it means a
very fast click during a lag spike could be missed entirely.

**Redundancy** (`NetworkClient::sendCommand`, `NetworkClient.cpp:43-63`): the client keeps
a rolling window of the last 3 commands in `recentCommands[3]`, shifts left each send, and
transmits **all three** in one `CommandPacket`. So each command is transmitted 3 times
across 3 consecutive packets. Two consecutive packets can be lost with zero input loss.
This is the standard Quake3/Overwatch-style trick and it's implemented correctly.

`sequence` is assigned here, monotonically from `nextSequence` starting at **1**
(`NetworkClient.h:39`) — 0 is reserved as the "empty slot" sentinel so the server can skip
unfilled entries in a fresh `CommandPacket`.

**Server intake** (`Server.cpp:95-123`): on `ENET_EVENT_TYPE_RECEIVE`, the server looks up
`playerIndex` from `event.peer->data`, then loops the 3 commands and pushes each into
`pendingCommands[playerIndex]` (a `std::deque<InputCommand>`) **only if**:
- `c.sequence != 0` (not an empty slot), and
- `c.sequence > highestRecieved[playerIndex]` (not a duplicate/reorder).

That second check is the de-duplication that makes redundancy safe. The queue is then
trimmed to a maximum of **8** entries by dropping from the front (`Server.cpp:113-116`) —
so if a client floods or the server stalls, stale input is discarded rather than causing
a growing input-lag backlog.

**Server consumption** (`Server.cpp:160-182`): exactly **one command per player per tick**.
If the queue is empty (input starvation from packet loss), the server reuses
`lastApplied[i]` but **strips all edge-triggered fields** — `primaryPressed`,
`secondaryPressed`, `dash`, `jump`, `equipWeapon`, `equipAbility` are forced false. This
prevents a lost packet from causing a repeated shot or an infinite bunny-hop. Held/analog
state (movement direction, look direction, `crouch`, `*Held`) *is* carried forward, so the
player keeps running in a straight line rather than stopping dead. This is a well-judged
design.

Crucially, on a starved tick `lastAppliedSequence[i]` is **not advanced**
(comment at `Server.cpp:178`). This is what makes reconciliation correct: the client must
not think the server consumed an input it never received.

**Command buffering means input delay.** The queue holds up to 8 commands and drains one
per tick, so in steady state the server is applying input that is somewhere between 0 and
8 ticks (0–133 ms) old, depending on jitter. There is no adaptive buffer sizing — this is
a fixed, generous window traded for smoothness.

### 4.5 Server → Client: snapshots

**`Snapshot`** (`engine/include/Snapshot.h:28-36`) — built fresh every tick at
`Server.cpp:185-233`:

```
tick            unsigned int      server tick counter (monotonic from 0)
playerCount     int
players[2]      PlayerSnapshot    FIXED SIZE — hard cap of 2 players
roundWins[2]    int
phase           int               RoundPhase cast to int
entityCount     int
entities[16]    EntitySnapshot    FIXED SIZE — hard cap of 16 entities
```

**`PlayerSnapshot`** (`Snapshot.h:5-18`) carries the full physics state needed for
reconciliation, not just position:

```
lastAppliedSequence  unsigned int   ← THE reconciliation key
position, velocity, lookDirection, dashDirection   glm::vec3
health, dashTimeLeft, dashRechargeTimer            float
dashCharges          int
grounded, sliding    bool
```

`lastAppliedSequence` is per-player and is what lets the client know exactly how far the
server has progressed through *its* input stream. This is the single most important field
in the netcode.

**`EntitySnapshot`** (`Snapshot.h:20-26`):

```
type       int    EntityType cast to int
position   glm::vec3
rotationY  float
isRed      bool
isAmber    bool
```

`rotationY`, `isRed` and `isAmber` are TrafficLight-specific fields living in a supposedly
generic struct. `Server.cpp:213-230` carries your two `ISSUE` comments about exactly this:
the loop iterates `WorldEntity*` (which has no `getRotationY()`), so it does a
`static_cast<TrafficLightEntity*>` behind an `if (getType() == TrafficLight)` and
hard-codes the field extraction. The clean fix is a virtual
`virtual void writeSnapshot(EntitySnapshot&) const` on `WorldEntity` — this is TODO #10 in
your dev notes ("Fix WorldEntity class so we can access the inheriting classes methods").

Fixed-size arrays are deliberate — `learning/netcode.md` explains it. `Snapshot` is
therefore a fixed **~200-byte** POD sent 60×/sec ≈ 12 KB/s per client. Cheap.

The 16-entity cap is enforced with `if (snapshot.entityCount >= 16) break;`
(`Server.cpp:210`) — entities beyond 16 silently vanish from clients while still
simulating server-side. Given `TrafficLight` has 1 charge per round and 2 players, you're
nowhere near the cap yet.

### 4.6 The connection handshake

1. Client `main()` constructs `NetworkClient` and immediately calls
   `connectToServer("127.0.0.1", 7777)` (`main.cpp:87-91`). This blocks for up to **5000 ms**
   waiting for `ENET_EVENT_TYPE_CONNECT` (`NetworkClient.cpp:31`). On failure the program
   exits before opening a window.
2. Server gets `ENET_EVENT_TYPE_CONNECT` (`Server.cpp:71`), assigns
   `playerIndex = nextPlayerIndex++`, stashes it in `event.peer->data` via the
   `(void*)(intptr_t)` int-in-a-pointer trick, and sends a reliable `Welcome`.
3. Client `poll()` receives `Welcome`, sets `myPlayerIndex` (`NetworkClient.cpp:84-88`).
4. Until step 3 completes, `myPlayerIndex` is `-1` and both
   `PlayingState::update()` (`PlayingState.cpp:77`) and `::render()`
   (`PlayingState.cpp:225`) early-return. **Nothing at all happens on the client until
   the Welcome lands** — including rendering, so you get a frozen/blank screen briefly.

**Note the double-connect.** `main.cpp:88` connects, and then `StateManager::performTransition()`
calls `network.connectToServer(pendingHost, pendingPort)` *again* when entering
`Pending::Match` (`StateManager.cpp:47`). Since `main.cpp` starts in the Menu state and
Enter transitions to Match, the client connects twice on the same `ENetHost`. The second
`enet_host_connect` overwrites the `peer` member with a new peer. This is almost certainly
vestigial from before `StateManager` existed and is worth cleaning up — see §14.

### 4.7 Client prediction (the local player)

Located in the fixed-timestep block, `PlayingState.cpp:147-200`.

```cpp
tickAccumulator += deltaTime;
while (tickAccumulator >= TICK_RATE) {          // TICK_RATE = 1/60, PlayingState.h:56
    tickAccumulator -= TICK_RATE;
    InputCommand command = <sample keyboard/mouse>;
    unsigned int seq = network.sendCommand(command);   // assigns & sends
    command.sequence = seq;
    commandHistory[seq % COMMAND_HISTORY_SIZE] = command;   // ring buffer, size 64

    resetPlayerStats(gameState.players[myIndex]);
    previousPosition = gameState.players[myIndex].position;
    processPlayerInput(gameState, myIndex, command, TICK_RATE);   // ← SHARED sim code
}
```

Points worth internalising:

- **The client runs the identical `processPlayerInput()` the server runs.** Same
  acceleration constants, same collision resolution, same dash/slide rules. This shared
  code is what makes prediction converge.
- `TICK_RATE` (1/60) is passed as `deltaTime`, **not** the real frame delta. Fixed timestep
  → determinism.
- `commandHistory` is a 64-slot ring indexed by `seq % 64` (`PlayingState.h:58-59`).
  64 ticks ≈ **1066 ms** of replay history. If the round-trip ever exceeds that, the
  history slot has been overwritten and reconciliation silently skips it (see below).
- `resetPlayerStats()` is called *before* every predicted tick, exactly mirroring
  `Server.cpp:146-148`. This resets `moveSpeed`/`gravity`/etc. from the `base*` values so
  item passive modifiers can re-apply cleanly each tick without compounding.
- `previousPosition` is captured pre-tick for **render interpolation** (§4.9), not for
  netcode.

### 4.8 Server reconciliation (the correction)

`PlayingState.cpp:89-145`. Runs once per snapshot, gated on `snap.tick != lastReconciledTick`
so a frame that renders twice between packets doesn't reconcile twice.

The sequence, in order:

**Step 0 — rebuild colliders.** `PlayingState.cpp:82-87` clears and rebuilds
`gameState.colliders` from `level.objects` *before* reconciliation, because the replay
runs real collision detection and needs them present.

**Step 1 — remember the prediction.**
```cpp
glm::vec3 predictedPosition = gameState.players[myIndex].position;
```

**Step 2 — snap remote players hard.** For every `i != myIndex`, position, lookDirection,
health and sliding are overwritten from the snapshot with **no prediction and no smoothing**
(`PlayingState.cpp:99-107`). This is deliberate: remote players are drawn from the
*interpolation buffer* instead (§4.9), so `gameState.players[i]` is only a fallback.

**Step 3 — rewind self to authority.** `PlayingState.cpp:110-120` overwrites the local
player's position, velocity, grounded, health, sliding, dashTimeLeft, dashCharges,
dashRechargeTimer and dashDirection with the server's values. The client's prediction is
discarded wholesale.

**Step 4 — replay unacknowledged input.**
```cpp
for (unsigned int seq = s.lastAppliedSequence + 1; seq < network.getNextSequence(); seq++) {
    InputCommand &c = commandHistory[seq % COMMAND_HISTORY_SIZE];
    if (c.sequence != seq) continue;      // slot was overwritten — history too short
    resetPlayerStats(me);
    processPlayerInput(gameState, myIndex, c, TICK_RATE);
}
```
This re-runs every command the server hasn't acknowledged yet, on top of the authoritative
state. The `c.sequence != seq` guard is the ring-buffer-overrun check: if RTT exceeded
~1 second the slot holds a newer command and it's skipped (which will produce a visible
correction, but not a crash).

**Step 5 — copy scoreboard.** `roundWins[0]` and `[1]` are copied from the snapshot
(`PlayingState.cpp:133-134`). **`snap.phase` is deliberately not copied — see §14.1, this
is a real bug.**

**Step 6 — measure and smooth the error.**
```cpp
glm::vec3 error = predictedPosition - gameState.players[myIndex].position;
if (glm::length(error) > 2.0f) positionError = glm::vec3(0.0f);   // too big → hard snap
else                           positionError += error;            // accumulate for smoothing
```
Then, every frame (outside the snapshot gate, `PlayingState.cpp:203`):
```cpp
positionError = glm::mix(positionError, glm::vec3(0.0f), 10.0f * deltaTime);
```
`positionError` is added to the **camera position only** (`PlayingState.cpp:213-214`), never
to the simulation position. So collision and physics always use the corrected authoritative
position, while the *view* decays the error to zero over roughly 100 ms. A player being
teleported by 1.9 m sees a smooth glide; 2.1 m and they get an instant snap. This is
textbook error-smoothing and it's implemented correctly.

`positionError` accumulates (`+=`) rather than being assigned, so successive small
corrections in the same direction compound into the visual offset — correct, because each
correction is a fresh delta on top of an already-offset view.

### 4.9 Remote player interpolation

`NetworkClient::getInterpolatedPlayer()` (`NetworkClient.cpp:95-120`) plus the call site
`PlayingState.cpp:345-356`.

The client keeps `std::deque<TimedSnapshot> snapshotBuffer` (`NetworkClient.h:43`), capped
at **32** entries (~533 ms of history, `NetworkClient.cpp:79`). Each entry pairs the
snapshot with `recievedTime` — the client's `glfwGetTime()` **at the moment of arrival**.

Render time is deliberately set **100 ms in the past**:
```cpp
float renderTime = (float)glfwGetTime() - 0.1f;   // PlayingState.cpp:228-230
```
The function scans the buffer for the consecutive pair straddling `renderTime`, computes
`alpha`, and `glm::mix`es `position` and `lookDirection`. `health` and `sliding` are taken
from the *later* snapshot rather than blended (correct — they aren't spatially continuous).

This 100 ms delay is what commit `28e79a9` ("added 100ms delay to interp player positions.
fixed client player jitter") introduced. It buys you ~6 ticks of buffer so that jitter and
one or two dropped snapshots never leave you with nothing to interpolate between.

If `renderTime` falls outside the buffer (startup, or a stall > 100 ms), the function
returns `false` and the caller falls back to `gameState.players[i].position` — the raw,
un-interpolated latest snapshot value (`PlayingState.cpp:353-355`).

**Two things to know about this implementation:**

1. **It interpolates against client arrival times, not server tick times.** `recievedTime`
   is when the packet landed locally. Network jitter therefore translates directly into
   non-uniform interpolation spacing — a packet that arrives 5 ms late makes remote
   movement momentarily 5 ms slow, then fast. Using `snapshot.tick * (1/60)` as the
   timeline instead (with a local clock estimate) would remove this. Not urgent at
   localhost latency; it will show up over a real network.
2. **Line 102 uses `&` instead of `&&`:**
   ```cpp
   if (earlier.recievedTime <= renderTime & renderTime <= later.recievedTime)
   ```
   Bitwise AND on two `bool`s happens to give the right answer (both operands promote to
   0/1), so this *works* — but it defeats short-circuiting and is a typo, not a choice.

### 4.10 What is and isn't authoritative

| Thing | Authority | Predicted client-side? |
|---|---|---|
| Player movement, collision, jump | Server (`processPlayerInput`) | **Yes** — full prediction + reconciliation |
| Dash charges / timing | Server | **Yes** — full state is in `PlayerSnapshot` |
| Slide state | Server | **Yes** |
| Look direction | Client-supplied, server accepts verbatim | n/a |
| Hitscan / damage (`Pistol::use`) | Server only | **No** — client `weapon` is `nullptr` |
| Item passive buffs (`ButterflyKnife`) | Server only | **No** — see §14.2 |
| `frozen` (TrafficLight effect) | Server only | **No** — dev-notes TODO #1 |
| World entity physics & lights | Server only (`updateWorld`) | **No** — rendered from snapshot |
| Round/match phase, scoring | Server only (`updateRound`) | **No** — `phase` not copied, see §14.1 |
| Item assignment (`giveRoundItems`) | Server only | **No** |

There is **no lag compensation / server-side rewind** for hitscan. `Pistol::use()` raycasts
against the players' *current* server positions at the moment the command is applied. Since
the server applies input 0–8 ticks late and the shooter aimed at where they saw the target
100 ms in the past (interpolation delay), you must currently lead your shots. Implementing
rewind would mean the server keeping a ring of historical player AABBs and raycasting
against the positions matching the shooter's `renderTime`. That's a substantial and
well-defined future task.

## 5. File-by-file: `engine/include/`

### `AABB.h` (54 lines) — collision primitives, header-only

- **`struct AABB`** — `glm::vec3 min, max`. Two opposite corners. Plain data, no methods.
- **`inline bool aabbOverlap(const AABB&, const AABB&)`** — separating-axis test on all
  three axes; returns true if they overlap on all three simultaneously.
- **`inline bool rayIntersectsAABB(origin, direction, box, float& tHit)`** — the **slab
  method** raycast. For each axis it computes the two `t` values where the ray crosses the
  min and max planes, swaps if the direction is negative, and narrows `[tMin, tMax]`. If
  `tMin > tMax` at any point, miss. Handles the degenerate `|direction[axis]| < 1e-6`
  case (ray parallel to that axis) by checking the origin is inside the slab and
  `continue`ing. On hit, writes the distance into `tHit`.

  `tMin` starts at `0.0f`, so the ray is a **half-line** — geometry behind the origin is
  never hit. Correct for both hitscan and LOS.

**Netcode relevance:** used by both roles. The server uses it in `Pistol::use` for hitscan
and in `resolveAABBCollision` for physics; the client uses the same functions during
prediction and replay. Determinism across both is what makes reconciliation converge.

`learning/AABB.md` is the accompanying note.

### `Utils.h` (18 lines) — line-of-sight, header-only

- **`inline bool hasLineOfSight(from, to, colliders)`** — normalises the delta, raycasts
  against every collider, returns false if any hit is *closer than* the target distance.
  Early-returns true if the two points are within 1e-6.

  **Gotcha:** this header uses `AABB`, `std::vector` and `FLT_MAX` but includes **nothing**.
  It compiles only because every translation unit that includes it has already included
  `AABB.h` and `<vector>`. `Bot.cpp`, `Pistol.cpp`, `TrafficLightEntity.cpp` and
  `Simulation.cpp` all get away with it. Adding `#include "AABB.h"` + `<vector>` would make
  it self-contained. The file's own comment says *"probably move to AABB.h idk"* — that
  would also solve it.

Used by: `Bot.cpp` (can the bot see its target), `Pistol.cpp` (indirectly — Pistol actually
does its own inline wall check rather than calling this), `TrafficLightEntity.cpp` (is the
player actually looking at a lit red light).

The most important header in the project. Everything simulation-related flows through here.

**`enum class EquipSlot { Weapon, Ability }`** — a player holds exactly two items and
toggles between them (keys 1 and 2).

**`enum class RoundPhase { Active, RoundOver, MatchOver }`** — the match state machine.

**`struct PlayerState`** — the full per-player simulation state:

| Field | Default | Notes |
|---|---|---|

| `velocity` | (0,0,0) | world units/sec |
| `lookDirection` | (0,0,-1) | normalised aim vector, set from client input |
| `health` | 100.0f | but `resetRound` sets it to **120.0f**, and the UI divides by 120 — see §14.5 |

### `Item.h` (21 lines) — the item interface

```cpp

    virtual ~Item() {}
    virtual void use(GameState&, int holderIndex, UseType) = 0;      // pure — must implement
    virtual void passiveUpdate(GameState&, int holderIndex, float dt) {}  // optional
    virtual void tickInternal(float dt) {}                            // optional — cooldowns

```

The four-method split is well thought out:
- `use()` — the discrete action (fire, throw).
- `passiveUpdate()` — per-tick modifiers written into `PlayerState`'s live stats.

- `isAlwaysActive()` — if true, `passiveUpdate()` runs even when the item is holstered.

## 6. File-by-file: `engine/src/`

### `Simulation.cpp` (474 lines) — **the heart of the game**

The single most important file. Compiled into `libengine.a`, therefore linked into both the
server and the client, and executed by both.

Five `static` (internal-linkage) helpers are forward-declared at the top with a comment
noting that a header would be nicer.

#### `processPlayerInput(GameState&, int playerIndex, const InputCommand&, float dt)`

The per-player, per-tick entry point. Executes in this exact order — the ordering is
deliberate and load-bearing:

1. **Phase gate** (`:28-29`): `if (state.phase != RoundPhase::Active) return;` — no
   movement between rounds or after the match. **The client never sets `phase`, so this
   gate never fires client-side. See §14.1.**
2. **Assign look direction** (`:33`): `player.lookDirection = command.lookDirection` —
   verbatim, unvalidated.
3. **Slide enter/exit** (`:46-56`): enters if not sliding + `crouch` held + grounded +
   horizontal speed > `slideMinSpeed` (3.0). Entry multiplies horizontal velocity by
   `slideEntryBoost` (**3.0×** — a big boost). Exits if crouch released or speed drops
   below 3.0.
4. **Dash charge recharge** (`:59-65`): if below `maxDashCharges` (**2**), accumulate
   `dashRechargeTimer`; at `dashRechargeTime` (1.5 s) grant a charge and reset the timer.
5. **Equip switching** (`:68-74`): weapon first, then ability — the comment explains this is
   in case the newly-equipped item modifies movement below.
6. **Item ticking** (`:79-84`): `tickInternal(dt)` on **both** weapon and ability
   unconditionally — cooldowns run while holstered.
7. **Item passive updates** (`:86-98`): `passiveUpdate()` runs for an item if it is the
   held one **or** `isAlwaysActive()`.
8. **Item use** (`:101-110`): `primaryPressed` (edge) → `use(Primary)`;
   `secondaryHeld` (level) → `use(Secondary)`. The comment notes this hard-codes LMB as
   semi-auto and RMB as full-auto — a per-item `isPrimaryAutomatic()` would generalise it.
9. **Dash initiation** (`:113-144`): requires `command.dash` (edge) + charges > 0 +
   `dashTimeLeft <= 0`. Direction is the normalised WASD intent projected onto the flat
   look basis; with no movement input it dashes straight forward. Sets
   `dashTimeLeft = dashDuration` (0.08 s).
10. **Movement resolution** — a three-way branch:
    - **Dashing** (`:146-151`): horizontal velocity is *overwritten* with
      `dashDirection * dashSpeed` (30.0 — nearly 4× walk speed). Normal input is ignored.
    - **Sliding** (`:152-189`): applies `slideFriction` (0.995/tick — very slow decay,
      ~0.3%/tick ≈ 17%/sec), adds weak steering (`slideSteer` 3.0 × dt), and allows a
      **slide-hop**: jumping while sliding gives `jumpStrength + horizontalSpeed/3`, i.e.
      speed converts into height. This is the movement-tech skill expression.
    - **Normal** (`:191-195`): `applyMovementInput()`.
11. **Gravity** (`:197`): `velocity.y += gravity * dt`. Applied *after* the branch, so it
    affects dashes and slides too.
12. **Collision** (`:198`): `resolvePlayerCollisions()`.

**Constants worth knowing** (all hard-coded locals inside the function):
`slideMinSpeed 3.0`, `slideEntryBoost 3.0`, `slideFriction 0.995`, `slideSteer 3.0`,
`maxDashCharges 2`, `dashRechargeTime 1.5`, `dashDuration 0.08`, `dashSpeed 30.0`.

#### `resetPlayerStats(PlayerState&)` (`:201-211`)

Copies all five `base*` values into the live values and clears `frozen`. Must be called
before `processPlayerInput` each tick — the server does it at `Server.cpp:146-148`, the
client at `PlayingState.cpp:129` (in replay) and `:196` (in prediction).

#### `updateWorld(GameState&, spawns, dt)` (`:213-234`)

**Server-only in practice.** Three phases:
1. `update(state, dt)` on every `WorldEntity*`.
2. Lifetime sweep: `delete` any entity where `isExpired()`, null the slot.
3. `erase(remove(..., nullptr), end())` — the erase-remove idiom to compact the vector.
4. Calls `updateRound()`.

#### `getPlayerAABB(const PlayerState&)` — static (`:238-245`)

`min = position + (-0.3, 0.0, -0.3)`, `max = position + (0.3, 1.8, 0.3)`.
**Player is 0.6 × 1.8 × 0.6, and `position` is at the feet.**

Note this function is `static` and therefore invisible to `Pistol.cpp`, which duplicates
the identical box construction inline at `Pistol.cpp:29-31` with a comment acknowledging
the duplication. If you ever change hitbox size you must change it in **three** places:
here, `resolvePlayerCollisions` (`:307-308`), and `Pistol.cpp`. Worth hoisting into
`Simulation.h` — this is dev-notes TODO #4-adjacent ("improved player hitboxes" in README).

#### `applyMovementInput(PlayerState&, const InputCommand&, float dt)` — static (`:249-300`)

The normal ground/air movement model. Descended from the old `Player::handleInput` (see
`learning/old_PlayerCPP.md` — a near-identical body, but reading a `GLFWwindow*` instead of
an `InputCommand`; that refactor is commit `1cfae1c`).

1. Build a flat basis: `flatFront` = lookDirection with `y = 0`, normalised;
   `flatRight = normalize(cross(flatFront, up))`.
2. Accumulate WASD into `moveDir` — **but only `if (!player.frozen)`**. This is where the
   TrafficLight freeze takes effect.
3. Normalise `moveDir` (so diagonals aren't faster).
4. `targetVel = moveDir * moveSpeed`.
5. Pick `accel = grounded ? groundAccel : airAccel` (12 vs 2 — heavy air control penalty).
6. `t = clamp(accel * dt, 0, 1)`; `velocity.xz = mix(velocity.xz, targetVel.xz, t)`.
   Exponential approach, not instant — this is the "weighty" feel.
7. Jump: `if (command.jump && grounded && !frozen) velocity.y = jumpStrength`.

Note jump is **level-triggered** (`command.jump` is `GLFW_PRESS` state, not an edge), so
holding space auto-bunnyhops. The server's starvation handler explicitly strips `jump`
(`Server.cpp:175`) to stop a lost packet from causing repeat hops.

#### `resolvePlayerCollisions` — static (`:303-310`)

A thin wrapper that calls `resolveAABBCollision` with the player's box extents and assigns
the return value to `player.grounded`.

#### `resolveAABBCollision(...)` (`:312-365`) — **public**

The physics core. Shared by players *and* thrown entities.

1. `position += velocity * deltaTime` — move on all axes first.
2. `grounded = false` (assume airborne).
3. For each collider that overlaps:
   - Compute penetration depth on each axis (`px`, `py`, `pz`).
   - Compare box centres to determine the push sign.
   - **Resolve along the shallowest axis only**, zeroing that axis's velocity.
   - If resolving on +Y (pushed up), set `grounded = true`.

This is a **discrete, non-swept** resolver — a fast enough object can tunnel through thin
geometry in one tick. At 60 Hz and dash speed 30, a tick moves 0.5 units, so anything
thinner than 0.5 units is tunnellable. All current level boxes are ≥ 2 units thick, so it's
not biting yet.

Resolving iteratively per-collider (rather than finding the single deepest first) means
corner cases can push twice in one tick. In practice it behaves fine.

**Netcode relevance:** this function's *exact determinism* is the load-bearing assumption
of the whole reconciliation scheme. Both sides run identical float math with identical
inputs and an identical `deltaTime` of exactly `1.0f/60.0f`. The collider *order* also
matters (resolution is order-dependent), and both sides build `colliders` by iterating
`level.objects` in JSON order — so they match, **provided both load the same level file**.
That's dev-notes TODO #6, and see §14.3.

#### `resetRound(GameState&, spawns)` — static (`:367-378`)

Sets both players to `health = 120.0f`, zeroes velocity, teleports to `spawns[i]`, then
`delete`s and clears all world entities.

**Note:** it does **not** re-give items. `Server.cpp:153-157` handles that separately by
watching the `RoundOver → Active` phase edge. It also does not reset `dashCharges`,
`dashTimeLeft`, `sliding` or `frozen` — a player who dies mid-dash respawns with the dash
timer still running.

#### `updateRound(GameState&, spawns, dt)` — static (`:380-465`)

The match state machine.

**`Active`:** scans for `health <= 0`. If exactly one player is dead, the *other* wins. If
both are dead in the same tick, `winner = 2` = a **double-KO**, and *both* score a point
(`:403-405`). If nobody is dead, early-return.

Then the win conditions:
- `a >= 7 && a - b >= 2` → player 0 wins the match (first to 7, win by 2).
- `b >= 7 && b - a >= 2` → player 1 wins.
- `a + b >= 20` → hard cap; higher score wins, tie → `matchWinner = -1` (a draw).
- Otherwise → `phase = RoundOver`, `phaseTimer = 2.0f`.

**`RoundOver`:** decrements `phaseTimer`; at ≤ 0 calls `resetRound()` and returns to
`Active`. So there's a 2-second intermission.

**`MatchOver`:** empty. Dev-notes TODOs #8 and #9 ("Plan the round win phase" / "Plan the
match win phase") are exactly this — the match ends and the server just sits there forever
in a state where `processPlayerInput` early-returns, meaning **both players are frozen with
no UI telling them why**. Getting out of `MatchOver` (back to menu, rematch) is unimplemented.

`matchWinner` is set but is **not in `Snapshot`**, so the client can never display who won.

#### `computeFlatMoveDirection` — static (`:467-474`)

Trivial helper: lookDirection with `y = 0`, normalised. Duplicated inline inside
`applyMovementInput` rather than called from there.

### `Camera.cpp` (68 lines) + `Camera.h`

A standard FPS fly-camera.

- **Constructor**: `front = (0,0,-1)`, `up = (0,1,0)`, `yaw = -90`, `pitch = 0`,
  `speed = 5`, `sensitivity = 0.1`.
- **`getViewMatrix()`**: `glm::lookAt(position, position + front, up)`.
- **`processKeyboard(window, dt)`**: WASD moves `position` directly.
  > **⚠ Dead code.** Nothing calls it. Player movement now goes through
  > `Simulation.cpp`, and `PlayingState::update()` **overwrites `activeCamera.position`
  > every single frame** (`PlayingState.cpp:213`). Any movement this applied would be
  > erased in the same frame.
- **`processMouse(xoffset, yoffset)`**: scales by sensitivity, accumulates yaw/pitch,
  clamps pitch to ±89° (avoiding gimbal flip at ±90), calls `updateVectors()`.
- **`updateVectors()`**: standard spherical → cartesian.
  `x = cos(yaw)cos(pitch)`, `y = sin(pitch)`, `z = sin(yaw)cos(pitch)`, normalised.

**Netcode relevance — important:** `Camera::front` is the *only* source of aim. It's
written by the GLFW mouse callback in `main.cpp` (which reaches the camera via
`glfwGetWindowUserPointer`), read into `command.lookDirection` at `PlayingState.cpp:159-160`,
and shipped to the server. And `Camera::position` is written from
`renderPos + positionError + (0, cameraHeight, 0)` (`:213-214`) — meaning **what you see is
the interpolated, error-smoothed position, not the simulation position**. This decoupling is
what makes movement look smooth despite 60 Hz ticks and server corrections.

### `GameObject.cpp` (56 lines)

- **Constructor**: plain member assignment.
- **`getAABB()`**: `min = position - size*0.5`, `max = position + size*0.5`. So
  `GameObject::position` is the **centre** — the opposite convention to
  `PlayerState::position` (feet). Easy to trip over.
- **`draw(Shader&)`**: calls `shader.use()`, builds `model = translate(position) * scale(size)`,
  uploads `model`, binds `material.texture` to slot 0, uploads `tint` and `textureScale`,
  sets `u_UseEmissive = 0` and `u_AlbedoMap = 0`, then `mesh->draw()`.

Every draw does 5 `glGetUniformLocation` calls, which are string lookups into the driver.
For 5 level boxes this is irrelevant; at hundreds of objects you'd cache the locations in
the `Shader` class. `learning/accessing_uniforms.md` covers the mechanism.

### `Level.cpp` (49 lines)

`loadLevel(path, mesh, texture)` parses the JSON via nlohmann and builds a `Level`.

- **`boxes`**: reads `min`/`max`, converts to `centre = (min+max)*0.5` and `size = max-min`.
  Computes `textureScale = vec2(size.x, size.z) / 8.0f` so texel density stays roughly
  constant across differently-sized boxes (one texture tile per 8 world units). Note it
  uses `.x` and `.z` regardless of the box's dominant axis, so a tall thin wall gets a
  stretched texture — a known cosmetic limitation.
- **`spawns` / `items` / `lights`**: reads the `pos` array from each into the respective
  vector. `id` and `name` fields are ignored.
- On file-open failure: prints and returns a default-constructed (empty) `Level`.
  **No exception, no exit** — the server would then have zero colliders and both players
  would fall forever. Worth an early `exit()`.

**Netcode relevance:** this function is the origin of `gameState.colliders` on *both* sides.
The rebuild loops are `Server.cpp:138-143` and `PlayingState.cpp:82-87` — identical logic,
identical order. Both currently hard-code `"test1v1level.level.json"`
(`Server.cpp:31`, `PlayingState.cpp:45`), each with its own literal. Dev-notes TODO #6 flags
that they can drift apart; §14.3 details the consequence.

### `Mesh.cpp` (77 lines)

**Constructor**: `vertexCount = vertices.size() / 8`. Creates and binds a VAO+VBO, uploads
with `GL_STATIC_DRAW`, then declares three attributes with stride `8 * sizeof(float)`:

| Location | Components | Offset | Meaning |
|---|---|---|---|
| 0 | 3 | 0 | position |
| 1 | 2 | 3 floats | UV |
| 2 | 3 | 5 floats | normal |

These match `basic.vert`'s `layout(location = ...)` declarations exactly.

**`draw()`**: bind VAO, `glDrawArrays(GL_TRIANGLES, 0, vertexCount)`. No index buffer —
vertices are fully duplicated per triangle. That's ~3× memory vs indexed, irrelevant at
current scale.

**`computeNormals(verts)`**: takes the 5-float layout, walks 3 vertices (15 floats) at a
time, computes `normalize(cross(B-A, C-A))` per face, and emits 8-float vertices with that
same flat normal on all three. **Flat shading only** — no vertex-normal averaging, so
smooth surfaces will facet. Used only for `Primitive::rawCubeVertices` (which wants flat
normals anyway). OBJ files skip this since `loadOBJ` already emits 8-float vertices with
the file's own normals.

`learning/cube_vertices.md` documents the primitive vertex layout.

### `OBJLoader.cpp` (83 lines)

`loadOBJ(path)` — a minimal Wavefront OBJ parser. Handles exactly four prefixes:

- `v` → `positions`, `vt` → `uvs`, `vn` → `normals`
- `f` → **exactly 3 corners** (`for (int i = 0; i < 3; i++)`), each parsed as `v/vt/vn` by
  splitting on `/`. Indices are converted from OBJ's 1-based to 0-based.

Outputs the flat 8-float engine layout directly.

**Limitations you will hit:**
- **Triangles only.** A quad face (`f a b c d`) silently loses its 4th vertex, corrupting
  the mesh. Export from Blender with "Triangulate Faces" ticked.
- **Requires all three components.** `std::stoi(vtStr)` throws on a face like `f 1//1`
  (no UV) — an uncaught `std::invalid_argument`, i.e. a crash.
- **No bounds checking** on `positions[vi]` etc. — a malformed index is UB.
- Ignores `usemtl`, `mtllib`, `o`, `g`, `s`. The `.mtl` files in `game/src/` are therefore
  **never read** — materials are set in C++.

Prints `"vertices floats: N"` on load; you'll see this three times at client startup.

### `Shader.cpp` (69 lines)

### `Texture.cpp` (60 lines)

Defines `STB_IMAGE_IMPLEMENTATION` — **this is the one and only translation unit that
compiles stb_image**, so don't add that define anywhere else.

- **Constructor**: generates + binds a texture, sets `GL_REPEAT` on S and T (tiling — needed
  for the `textureScale` trick), `GL_LINEAR` minification, `GL_NEAREST` magnification (so
  close-up textures stay crisp/pixelated — a deliberate style choice).
  Calls `stbi_set_flip_vertically_on_load(true)` because image rows run top-to-bottom while

  uploads, generates mipmaps. On failure prints the path and channel count and **leaves

  Frees the stb buffer at the end (safe even on the failure path — `stbi_image_free(nullptr)`

The `slot` parameter is what makes the albedo(0)/emissive(1) split in `PlayingState::render()`
work. `learning/textures.md` covers mipmaps and filtering.

### `UIRenderer.cpp` (87 lines)

Immediate-mode 2D overlay renderer. Owns three `Shader`s, constructed in a member
initialiser list: `shader("ui.vert","ui.frag")`, `fireShader("ui.vert","ui_fire.frag")`,

The server keeps ticking regardless, so the client falls behind on sequence numbers and
the next snapshot triggers a large correction. That's the right trade — a 200-tick catch-up
burst would be far worse — but it's why a long stall produces a visible snap.

### `StateManager.h` / `StateManager.cpp` (33 + 56 lines) — the screen state machine

```cpp
class StateManager {
    StateManager(GLFWwindow*); ~StateManager();
    void update(float dt); void render();
    void requestMenu(); void requestMatch(const char* host, int port);
    GLFWwindow* getWindow(); NetworkClient& getNetwork();
private:
    void performTransition();
    GLFWwindow* window;
    NetworkClient network;          // ← OWNED HERE, survives state swaps
    GameStateBase* currentState;
    enum class Pending { None, Menu, Match };
    Pending pending = Pending::None;
    const char* pendingHost; int pendingPort;
};
```

**The `NetworkClient` lives here by value**, exactly as your dev notes record: *"StateManager.h
also stores the NetworkClient network variable which means that the network will persist
between state swaps."* This is the right call — the ENet host and its connection outlive
any individual screen, so a menu→match→menu round trip doesn't tear down the socket.

`Pending` is the enumeration of every screen the game can enter (currently `Menu` and `Match`).

**The deferred-transition pattern** — this is the piece your dev notes flag as needing
documentation (TODO: *"StateManager::PerformTransition() needs documentation"*). Here it is:

- `requestMenu()` / `requestMatch()` only set `pending` (and the host/port). They do **not**
  switch state.
- `update(dt)` calls `currentState->update(dt)` **first**, then `performTransition()`.
- `performTransition()` (`StateManager.cpp:40-56`):
  1. `if (pending == None) return;`
  2. `delete currentState; currentState = nullptr;`
  3. If `Pending::Match` → `network.connectToServer(pendingHost, pendingPort)`, then
     `new PlayingState(window, network)`.
     Else → `new MenuState(window)`.
  4. `currentState->manager = this;` — wire the back-pointer.
  5. `pending = Pending::None;`

**Why deferred?** Because a state requests its own destruction from inside its own
`update()`. `MenuState::update()` calls `manager->requestMatch(...)`; if that deleted
`MenuState` immediately, `update()` would return into freed memory — a guaranteed
use-after-free. Deferring to *after* `update()` returns makes it safe. The code comment at
`StateManager.cpp:20` says exactly this: *"always transition after update so we dont do it
in the middle of smth"*.

**Two rough edges:**
- `pendingHost` is a `const char*` with no ownership. It currently only ever points at a
  string literal (`MenuState.cpp:13`), which has static lifetime, so it's safe — but the
  moment you build the host string dynamically (a server-browser text field) this becomes a
  dangling pointer. `std::string` would fix it.
- `performTransition` is called at the end of `update()` but `render()` is a *separate*
  call from `main`. Between them nothing can transition, so that's fine.

#### `update(float deltaTime)` (`:70-221`)

Fully documented in §4.7–4.9. Structure:
1. `uiTime += deltaTime` (drives the fire shader).
2. `network.poll(glfwGetTime())` — drain packets.
3. Early-return if `myIndex` is invalid (no Welcome yet).
4. Rebuild `gameState.colliders`.
5. **Reconciliation block** (gated on a new `snap.tick`).
6. **Fixed-timestep block** — sample input, send, predict.
7. **Per-frame smoothing** — `positionError` decay, `cameraHeight` lerp toward
   `sliding ? 0.8 : 1.7` at rate 12, render-position interpolation, camera placement,
   FOV lerp toward `(sliding || dashing) ? 85 : 70` at rate 8.

The render-position interpolation (`:209-212`) is worth calling out separately:
```cpp
float alpha = tickAccumulator / TICK_RATE;       // 0..1 progress into the next tick
glm::vec3 renderPos = glm::mix(previousPosition, players[myIndex].position, alpha);
```
This decouples the 60 Hz simulation from the (possibly 144 Hz) render rate. Without it you'd
see stepping at any refresh rate that isn't an exact multiple of 60. Combined with
`positionError`, the camera position is `mix(prev, cur, alpha) + error + eyeHeight`.

The `cameraHeight` and `currentFov` lerps are the "juice": crouching drops the eye height
smoothly, and sliding/dashing widens the FOV to 85° for a speed sensation. Both are
frame-rate-dependent lerps (`rate * deltaTime`), which is approximately correct at stable
framerates.

#### `render()` (`:223-474`)

1. Early-return if `myIndex < 0`.
2. `renderTime = glfwGetTime() - 0.1f` (the interpolation delay).
3. Clear to black; clear colour **and** depth buffers.
4. Query framebuffer size, compute aspect.

   > **Note the far plane is 100.0.** The ground plane in `test1v1level` spans ±46 units,
   > so its far corners (~65 units diagonal) are inside it, but only just. A larger level

      > intentional; see the `WARNING` comment in `basic.frag:64-66`.

#### The tick loop (`:61-255`)

**Pacing** (`:62`, `:254`): `nextTick += microseconds(16667)` at the top, and
`std::this_thread::sleep_until(nextTick)` at the bottom. Because `nextTick` accumulates from
a fixed origin rather than being recomputed from "now", timing errors **do not drift** —
a tick that overruns is absorbed by the next sleep being shorter. If the server ever falls
more than one tick behind, `sleep_until` returns immediately and it runs back-to-back ticks
to catch up. Solid design.

> 16667 µs = 60.0012 Hz, a negligible 0.002% fast against the client's exact `1.0f/60.0f`.

**Phase 1 — drain the network** (`:67-134`): `while (enet_host_service(server, &event, 0) > 0)`.
The `0` timeout means "poll, never block" — critical, since blocking would stall the
simulation.
- `CONNECT` → assign index, stash in `peer->data`, send reliable `Welcome`.
- `RECEIVE` → size-check, dedup, enqueue, trim to 8, `enet_packet_destroy`.
- `DISCONNECT` → prints a message and **nothing else** (the slot is not freed, `nextPlayerIndex`
  is not decremented). See §14.4.

**Phase 2 — rebuild colliders** (`:138-143`): clear and repopulate from `level.objects`
every tick. Since the level is static this is pure redundant work (5 boxes, so ~nothing),
but it's the same code path the client runs, which keeps ordering identical. Would matter
if you ever added moving geometry.

**Phase 3 — reset stats** (`:146-148`): `resetPlayerStats(p)` for both, so item passives
re-apply cleanly.

**Phase 4 — `updateWorld(gameState, level.spawns, tickRate)`** (`:150`): entity ticking,
lifetime sweep, round logic. **This runs *before* player input**, so entities see last
tick's player positions. A one-tick lag, irrelevant at 60 Hz.

**Phase 5 — round-restart edge** (`:153-158`): if `previousPhase == RoundOver && phase == Active`,
re-give items to both players. This is the only place items are refreshed mid-match.

**Phase 6 — apply one command per player** (`:160-182`): the queue-drain + starvation
fallback described in §4.4.

**Phase 7 — build and broadcast the snapshot** (`:185-241`): fills every field, iterates
world entities (with the two `ISSUE`-commented hard-coded casts), prefixes the type byte,
`enet_host_broadcast(server, 0, packet)` unreliable.

**Phase 8 — debug output** (`:244-251`): `if (tickCounter % 60 == 0 && 1 == 0)` — the
`&& 1 == 0` is a hard-coded "off" switch (the comment says so). Flip it to `1 == 1` to get
a once-per-second position dump for player 0.

**Phase 9 — sleep.**

#### Server-side observations

- **No fixed player cap on connect.** A third client gets `playerIndex = 2`.
  `pendingCommands` has size 2, so `if (playerIndex < pendingCommands.size())` (`:98`)

  `PlayingState.cpp:77` early-returns forever. So a third player gets a permanently frozen
  black screen rather than a clean rejection.
- **No timeout / disconnect handling** for the simulation. If player 0 quits, the server
  keeps simulating them as a starved (last-input-held) player forever.
- **No authentication, rate limiting, or input validation.** `lookDirection` is trusted
  verbatim and never normalised; a crafted client could send a zero vector, which would make
  `glm::normalize(flatFront)` produce NaN and poison that player's position permanently.
  Worth an early sanity check.
- **Items leak on shutdown** — `player.weapon`/`ability` are `new`'d and only `delete`d
  by the next `giveRoundItems`. Process exit reclaims it, so it's benign, but a
  `~PlayerState` or `std::unique_ptr<Item>` would be cleaner.

### `NetworkClient.h` / `NetworkClient.cpp` (43 + 119 lines) — **the client wire layer**

Public interface:
```cpp
NetworkClient();  ~NetworkClient();
bool connectToServer(const char* host, int port);
unsigned int sendCommand(InputCommand command);     // returns the assigned sequence
void poll(float currentTime);
bool hasSnapshot() const;
const Snapshot& getSnapshot() const;                // the LATEST snapshot
int getPlayerIndex() const;
unsigned int getNextSequence() const;               // for the replay loop bound
bool getInterpolatedPlayer(int idx, float renderTime, PlayerSnapshot& out) const;
struct TimedSnapshot { Snapshot snapshot; float recievedTime; };
```

Private: `host`, `peer`, `latestSnapshot`, `snapshotRecieved`, `recentCommands[3]`,
`nextSequence = 1`, `myPlayerIndex = -1`, `deque<TimedSnapshot> snapshotBuffer`.

**Constructor** (`:5-11`): `enet_host_create(nullptr, 1, 2, 0, 0)`. Prints on failure but
does **not** throw — a null `host` then makes `poll()` early-return silently.

**Destructor** (`:13-17`): `enet_host_destroy(host)`. Note `peer` is not explicitly
disconnected — no graceful `enet_peer_disconnect` handshake, so the server only notices via
timeout.

**`connectToServer`** (`:19-41`): resolves the host, `enet_host_connect(host, &address, 2, 0)`,
then a **blocking** `enet_host_service(host, &event, 5000)` waiting for `CONNECT`. On
failure: `enet_peer_reset`, null the peer, return false.

**`sendCommand`** (`:43-63`): documented in §4.4. Returns the assigned sequence so the
caller can key its history ring. Returns 0 if `peer == nullptr` — and note `PlayingState`
does not check for that 0, so it would write to `commandHistory[0]` with sequence 0. Only
reachable if the connection failed, in which case nothing else works either.

**`poll(float currentTime)`** (`:66-92`): non-blocking drain.
- `Snapshot` → wraps in a `TimedSnapshot` with `recievedTime = currentTime`, pushes to
  `snapshotBuffer` (trimmed to 32), assigns `latestSnapshot`, sets `snapshotRecieved = true`.
- `Welcome` → sets `myPlayerIndex`.
- Always `enet_packet_destroy`.

> **Note:** out-of-order snapshots are **not** rejected. If snapshot N+1 arrives before N,
> `latestSnapshot` briefly goes backwards and the buffer's `recievedTime` ordering still
> holds (arrival order), so interpolation stays monotonic — but reconciliation would
> rewind to older authority for one frame. `snap.tick` is available; a
> `if (snap.tick <= latestSnapshot.tick) skip` guard would close this. UDP reordering on
> localhost is essentially nonexistent, which is why it hasn't bitten.

**`getInterpolatedPlayer`** (`:95-120`): documented in §4.9, including the `&` vs `&&` typo.

### `Item` implementations

#### `Pistol.h` / `Pistol.cpp` (20 + 85 lines) — hitscan weapon

```
public:  ammo = 18, damage = 12
private: primaryCooldown, primaryRate = 4.0    (→ 0.25s between shots)
         secondaryCooldown, secondaryRate = 25.0 (→ 0.04s, burst fire)
```

**`use(state, holderIndex, Primary)`** — the only place damage is dealt in the game:
1. Cooldown gate, ammo gate; decrement ammo, set `primaryCooldown = 1/primaryRate`.
2. Ray origin = `shooter.position + (0, 1.7, 0)` (eye height); direction = `lookDirection`.
3. Loop all other players, build their AABB **inline** (duplicating `getPlayerAABB`,
   with a comment acknowledging it), raycast, track the nearest hit.
4. Separately loop `state.colliders` and raycast; if any wall hit is **closer than**
   `hitDistance`, mark `blocked`.
5. If hit && !blocked → `state.players[hitPlayer].health -= damage`.

**`use(..., Secondary)`** — "burst fire": consumes ammo and prints, but **deals no damage
and performs no raycast**. Unimplemented.

**`tickInternal(dt)`** — decrements both cooldowns.

> **Header/definition mismatch:** `tickInternal` is declared `private` and `virtual` (without
> `override`) in `Pistol.h:12`. C++ virtual dispatch ignores access specifiers at the call
> site through a base pointer, so `Simulation.cpp:80` calling `player.weapon->tickInternal(dt)`
> through `Item*` works correctly. It's legal but unconventional; `public ... override`
> would be clearer and would catch signature typos at compile time.

**Netcode relevance:** all damage is server-side and instantaneous, with **no lag
compensation**. The wall-blocking check uses `hitDistance` which is `FLT_MAX` when no player
was hit — meaning `blocked` gets set by any wall at all in that case, but since
`hitPlayer == -1` the result is discarded anyway. Correct, if slightly wasteful.

Ammo is never replenished except by `giveRoundItems` at round start. 18 shots per round.

#### `ButterflyKnife.h` / `ButterflyKnife.cpp` (8 + 18 lines) — passive movement buff

**`passiveUpdate`**: multiplies the live stats —
`moveSpeed ×1.75`, `airAccel ×2.0`, `groundAccel ×1.25`, `gravity ×0.75`,
`jumpStrength ×0.8`. A mobility item: much faster, far better air control, floatier, with a
slightly weaker jump as the trade.

Multiplicative (not additive) so effects stack cleanly with any future items — the comment
says so explicitly.

**`use(Primary)`**: prints only. No melee attack implemented.

> **Not currently obtainable** — `giveRoundItems` hands out Pistol + TrafficLight. The

### `WorldEntity` implementation

#### `TrafficLightEntity.h` / `TrafficLightEntity.cpp` (29 + 93 lines)

The only concrete `WorldEntity`. A thrown object that lands and periodically turns red,
freezing anyone who looks at it. A Red-Light-Green-Light mechanic.

**State**: `collisionBoxMin/Max` = `(-0.3, 0.0, -0.3)` … `(0.3, 1.0, 0.3)` (0.6 × 1.0 × 0.6),
`timer`, `isRed`, `isAmber`, `lifetime`, `velocity`, `rotationY`, `spinSpeed`, `settled`.

**Constructor**: sets inherited `position` and `ownerIndex`, `lifetime = 22.0f`.
> The header default is `float lifetime = 0.0f` and the constructor overwrites it with 22.
> Note that a `TrafficLightEntity` constructed *without* going through this constructor
> would be instantly expired — not currently possible, but brittle.

**`update(state, dt)`**:
1. Gravity: `velocity.y += -20 * dt` — **hard-coded, not read from any shared constant**,
   though it happens to match `PlayerState::baseGravity`.
2. `resolveAABBCollision(position, velocity, collisionBoxMin, collisionBoxMax,
   state.colliders, dt)` — **reuses the exact player physics function.** This is the payoff
   of exposing it publicly in `Simulation.h`.
3. If grounded: damp `velocity.xz ×0.9` and `spinSpeed ×0.9` per tick. Below 0.1 horizontal
   speed, hard-zero everything and set `settled = true`.
   > `settled` is written but **never read**. Presumably intended to gate the light cycle
   > until it lands, or to stop physics work once at rest.
4. `rotationY += spinSpeed * dt` — cosmetic spin, snapshotted for the client.
5. `timer += dt; lifetime -= dt;`
6. **Light cycle** (`:46-61`): `isAmber` is true only when `!isRed && timer > 4.8`. At
   `timer >= 5.5` the light **toggles** `isRed` and resets `timer`. So the cycle is
   **5.5 s green (last 0.7 s amber as a warning) → 5.5 s red → repeat**, and with a 22 s
   lifetime that's exactly **two full green/red cycles**.
7. **Freeze check** (`:63-75`): only while `isRed`. For each player:
   - `toLight = normalize(position - player.position)`
   - `if (dot(player.lookDirection, toLight) > 0.4f)` — you're looking roughly toward it
     (0.4 ≈ within a 66° half-angle cone).
   - `hasLineOfSight(player.position + (0,1.7,0), position, state.colliders)` — no wall between.
   - → `player.frozen = true`.

   > **Note it freezes *everyone*, including the thrower.** `ownerIndex` is stored but never
   > checked here. Whether that's intended is a design decision.
   >
   > `frozen` is cleared every tick by `resetPlayerStats`, so it must be re-set every tick
   > — which the entity does, since `updateWorld` runs after the reset and before
   > `processPlayerInput`. The ordering in `Server.cpp` (reset at `:146` → `updateWorld` at
   > `:150` → input at `:160`) is exactly right, and this is a subtle dependency worth
   > preserving if you ever reorder that loop.

**`isExpired()`**: `lifetime <= 0.0f`.

**`getType()`**: `EntityType::TrafficLight`.

**`throwFrom(direction, speed, spin)`**: `velocity = direction * speed; spinSpeed = spin;`

**Netcode relevance:** the entity exists **only on the server**. The client never
instantiates one; it renders from `EntitySnapshot` (`PlayingState.cpp:289-341`). This means:
- Entity motion is **not** interpolated or predicted — it snaps to the latest snapshot
  position at whatever rate packets arrive. A thrown light in flight will look choppier
  than a player.
- The freeze effect is invisible to client prediction. You will keep predicting normal
  movement while the server holds you still, generating a correction every tick you're
  frozen. That's dev-notes TODO #1 (*"Make player 'freeze' effect, be also considered by
  the client"*), and it's the most user-visible prediction failure in the game right now.

`getIsRed()`, `getIsAmber()`, `getRotationY()` exist solely so `Server.cpp`'s snapshot
writer can read them after a `static_cast` — the ISSUE at `Server.cpp:213`.

### `Primitives.h` (60 lines)

`namespace Primitive { std::vector<float> rawCubeVertices = {...}; }` — 36 vertices
(6 faces × 2 triangles × 3), 5 floats each (`x y z u v`), in the range ±0.5, with per-face

## 10. File-by-file: shaders

All GLSL is `#version 330 core`, matching the 3.3 core context requested in `main.cpp`.

### `basic.vert` (32 lines) — the 3D vertex shader

Inputs: `layout(location=0) vec3 aPos`, `(1) vec2 aTexCoord`, `(2) vec3 aNormal` —
matching `Mesh.cpp`'s attribute setup exactly.
Uniforms: `mat4 model, view, projection`.
Outputs: `TexCoord`, `FragPos` (world space), `Normal`.

```glsl
gl_Position = projection * view * model * vec4(aPos, 1.0);
FragPos = vec3(model * vec4(aPos, 1.0));
Normal  = mat3(transpose(inverse(model))) * aNormal;
```

The `transpose(inverse(model))` is the **normal matrix** — necessary so normals stay
perpendicular under non-uniform scaling (which every level box has, since they're unit cubes
scaled to arbitrary sizes). Computing an inverse per-vertex is expensive; the standard
optimisation is to compute it CPU-side and upload it as a uniform. At current scale it's
fine. `learning/matrix.md` explains the transform chain.

### `basic.frag` (80 lines) — Phong + emissive

Uniforms: `sampler2D u_AlbedoMap, u_EmissiveMap`; `vec3 u_ActiveState`;
`float u_BloomIntensity`; `bool u_UseEmissive`; `vec2 textureScale`;
`vec3 lightPos, lightColor, viewPos, tint`.

1. `scaledUV = TexCoord * textureScale`; sample albedo.
2. **Phong lighting** (single point light, no attenuation — brightness doesn't fall off with
   distance):
   - Ambient: `0.35 * lightColor` (quite high — nothing is ever fully dark).
   - Diffuse: `max(dot(norm, lightDir), 0.0) * lightColor`.
   - Specular: `0.5 * pow(max(dot(viewDir, reflectDir), 0.0), 24.0) * lightColor`.
     (The comment says "pow 32" but the code uses 24.)
   - `litColor = (ambient + diffuse + specular) * objectColor * tint`.
3. **Emissive** (`if (u_UseEmissive)`): samples `u_EmissiveMap.rgb` as a **channel mask**,
   isolates the active channel with `dot(mask, u_ActiveState)`, then maps the active state
   to a display colour and multiplies by `u_BloomIntensity`.

The RGB-channel-mask design (commit `5dc190d`, "refactored emissive capability to use rgb
channels in masks") packs three independent emissive regions into one texture: red channel =
region 1, green = region 2, blue = region 3. `u_ActiveState` selects which lights up.

The `WARNING` comment at `:64-66` is important and accurate:
```
red channel   → displays (1.0, 0.1, 0.1)  red
green channel → displays (0.1, 1.0, 0.2)  green
blue channel  → displays (1.0, 0.8, 0.0)  AMBER
```
The channel→colour mapping is hard-coded in the shader, which is why the traffic light's
"amber" state selects the *blue* channel (`PlayingState.cpp:300`). The comment proposes the
fix: three uniforms (`vec3 redChannelEmissiveColour`, etc.) so materials define their own
mapping. Worth doing before adding a second emissive object.

`emissiveOutput` is *added* after lighting so it doesn't get shaded — it "glows".
There's no actual bloom post-process; `u_BloomIntensity = 5.0` just overdrives the colour
past 1.0, which clips to white at the centre and reads as glow. A real bloom pass would need
an HDR framebuffer + blur.

A commented-out normal-debug line sits at `:79`.
`learning/Phong_lighting.md` is the accompanying note.

### `ui.vert` (12 lines)

`layout(location=0) vec2 aPos` (the unit quad), uniforms `projection` (ortho) and `model`.
Passes `aPos` straight out as `TexCoord` — since the quad spans (0,0)–(1,1), the local
position *is* the UV. Neat.

### `ui.frag` (8 lines)

`FragColor = color;` — flat fill.

### `ui_circle.frag` (12 lines)

```glsl
if (length(TexCoord - 0.5) > 0.5) discard;
FragColor = color;
```
Discards outside the inscribed circle. Hard-edged (no anti-aliasing) — a `smoothstep` on
the distance and alpha modulation would smooth it.

### `ui_fire.frag` (82 lines) — procedural animated flame

Uniforms: `time`, `amount` (intensity, hard-coded to 5.0 by `UIRenderer`), `id` (random
seed, fed the pip index), `color1` (main), `color2` (hot).

Algorithm:
1. Early-out to transparent if `intensity < 0.1`.
2. Centre the UV, then **pixelate** by flooring to a 60×60 grid (`PIXEL_SIZE_FAC = 60.0`) —
   the deliberate chunky look.
3. Apply a sin/cos base distortion.
4. Build an upward-scrolling vector from `time` and `id`, so each pip's flame is
   out of phase.
5. **5-iteration fractal domain-warp loop** — repeatedly displaces `sv`/`sv2` with nested
   trig. This is the flame turbulence.
6. Compute a `smoke_res` density; `> 1.0` → fully transparent.
7. Colour: `color1` as base, blending toward `color2` in the lower region (`uv.y < 0.12`).

Recognisably a Balatro-style flame shader. It's the most expensive shader in the project by
far (5 iterations of nested transcendentals per fragment), but it only ever runs on a
handful of ~42×84 px quads.

### `gold-blue_cellular.frag` (421 lines) — **unused**

A large ShaderToy-derived cellular/voronoi effect. Ported with compatibility shims at the
top (`#define uResolution iResolution.xy`, output renamed to `oColor` "bc FragColor already
defined and we cant conflict"), plus a big block of hard-coded constants replacing the
original's uniform inputs (`clickPos`, `hoverEnable`, `tileScale`, etc.).

> **⚠ Not referenced by any C++ file.** `grep` finds no `Shader(...)` constructing it. It's
> a saved effect for future UI/background work.

## 14. Known gaps, desync risks, and dead code

Everything in this section is verified against the source. Ordered roughly by impact.

### 14.1 🔴 The client never reads `snap.phase` — guaranteed rubber-band at every round end

`Snapshot::phase` is filled by the server (`Server.cpp:206`) and **never read by the client**.
`grep -n "phase" game/src/PlayingState.cpp` returns nothing.

Consequence: `gameState.phase` on the client stays at its default `RoundPhase::Active`
forever. So during the 2-second `RoundOver` intermission:
- The **server** early-returns from `processPlayerInput` (`Simulation.cpp:28-29`) — players
  are frozen.
- The **client** keeps predicting full movement, because its phase gate never fires.

Every tick of those 2 seconds produces a fresh mispredict. And `resetRound` then teleports
both players to spawn, which is almost certainly a > 2.0 m error, triggering the hard-snap
path. So you get 2 seconds of fighting the server followed by a teleport, every single round.

**Fix:** one line in the reconcile block next to the `roundWins` copy:
```cpp
gameState.phase = (RoundPhase)snap.phase;
```
This is probably the single highest-value change in this document.

### 14.2 🔴 Items are never predicted — the client's `weapon`/`ability` are always `nullptr`

`giveRoundItems()` is called only from `Server.cpp`. The client's `PlayerState`s are default-
constructed at `PlayingState.cpp:63,67` with `weapon = ability = nullptr`.

So inside the client's `processPlayerInput`, `held` is null and the entire item block
(`Simulation.cpp:76-110`) is skipped. Consequences:
- **Passive stat modifiers are not predicted.** Right now the equipped items (Pistol,
  TrafficLight) have no `passiveUpdate`, so nothing breaks. But the moment you put
  `ButterflyKnife` in the loadout, the server moves you at 14.0 u/s while the client predicts
  8.0 u/s — a **persistent, every-tick position error** that reconciliation will fight
  continuously. The movement will feel like running through mud with constant snapping.
- **Shooting has no local feedback.** No prediction, so the only confirmation is the health
  bar changing several ticks later.

**Fix path:** call `giveRoundItems()` on the client too, driven by the same `RoundOver →
Active` phase edge (which requires §14.1 first). Item *state* (ammo, cooldowns) will still
diverge unless snapshotted — so start by predicting only `passiveUpdate` and leave `use()`
server-only.

### 14.3 🟡 Client and server load the level independently

Two separate hard-coded literals: `Server.cpp:31` and `PlayingState.cpp:45`, both currently
`"test1v1level.level.json"`. This is dev-notes TODO #6 and the `ISSUE` at `Server.cpp:30`.

If they ever differ, `gameState.colliders` differs, so `resolveAABBCollision` produces
different results, so **every single tick mispredicts** — the client would be permanently
rubber-banding with no obvious cause.

**Fix:** put the level name in the `WelcomeMessage` (it already exists and is reliable),
and have the client load whatever the server names. Cheap and closes the whole class of bug.

Related: **collider *order* also matters**, because `resolveAABBCollision` resolves
per-collider iteratively and is order-dependent. Both sides iterate `level.objects` in JSON
order, so they match today — but any future "sort colliders by distance" optimisation on one
side only would silently break determinism.

### 14.4 🟡 No disconnect handling

`Server.cpp:125-128` logs a disconnect and does nothing else:
- `nextPlayerIndex` is never decremented, so a reconnecting player gets index 2, then 3…
- Index 2+ receives a `Welcome` but has no `PlayerState`, so its client hits the
  `myIndex >= gameState.players.size()` guard (`PlayingState.cpp:77`) and freezes forever
  on a black screen.
- The disconnected player's `PlayerState` keeps simulating with held input.

**Fix sketch:** maintain a `bool slotTaken[2]`, clear it on disconnect, assign the lowest
free index on connect, and reject (`enet_peer_disconnect`) when both are taken.

### 14.5 🟡 Health default (100) vs round health (120) vs UI divisor (120)

Three places disagree:
- `GameState.h:20` — `float health = 100.0f`
- `Simulation.cpp:369` — `resetRound` sets `120.0f`
- `PlayingState.cpp:401` — UI divides by `120.0f`

So **the very first round starts at 100 HP but the bar renders 100/120 = 83% full.** Every
subsequent round is correct at 120. Fix by changing the default in `GameState.h` to 120 and
hoisting the constant.

### 14.6 🟡 `dashCharges` default (3) vs `maxDashCharges` (2)

`GameState.h:35` defaults to `3`, but `Simulation.cpp:40` caps recharging at `maxDashCharges = 2`.
So you start with 3 dashes and can never get the third back. `resetRound` doesn't reset
`dashCharges` at all, so from round 2 onward you have 2.

Not necessarily wrong (a first-round bonus?), but almost certainly unintentional.

### 14.7 🟡 The client connects twice

`main.cpp:88` calls `network.connectToServer(...)`, then `StateManager::performTransition`
calls it again on the same `NetworkClient` when entering `Pending::Match`
(`StateManager.cpp:47`). The second `enet_host_connect` overwrites `peer` — and since the
host was created with only **1 peer slot** (`NetworkClient.cpp:6`), the second connect may
well fail and null out a working peer, or leak the first.

Since it works in practice, the first connection is presumably still the live one. Either
way it's confusing: the connect in `main.cpp` predates `StateManager` and should be deleted,
leaving `StateManager` as the single owner of connection lifetime. Note that would also make
`MenuState`'s Enter key actually meaningful.

Related: `NetworkClient` has no `disconnect()`, so a menu→match→menu→match cycle would keep
piling up connects.

### 14.8 🟡 A dangling `Camera*` window user pointer

`PlayingState`'s constructor does `glfwSetWindowUserPointer(window, &activeCamera)`
(`PlayingState.cpp:43`), pointing at a member of the `PlayingState`. When
`StateManager::performTransition` does `delete currentState` (`StateManager.cpp:43`), that
pointer dangles — GLFW still holds it, and `mouse_callback` would dereference freed memory
on the next mouse move.

It hasn't crashed because there's currently no path *out* of `PlayingState` back to the menu.
The moment you add one (which §14.9 requires), this becomes a live use-after-free.

**Fix:** either clear it (`glfwSetWindowUserPointer(window, nullptr)`) in a `PlayingState`
destructor, or move the camera ownership out of the state.

### 14.9 🟡 `MatchOver` is a dead end

`updateRound`'s `MatchOver` branch is empty (`Simulation.cpp:462-464`), and
`processPlayerInput` early-returns for any non-`Active` phase. So when the match ends,
**both players are permanently frozen with no UI explanation** and no path back to the menu.
`matchWinner` is computed but isn't in `Snapshot`, so the client can't even display it.

Dev-notes TODOs #8 and #9. The pieces needed: add `matchWinner` to `Snapshot`, add a
`MatchOver` UI, and add a `StateManager::requestMenu()` path out of `PlayingState`.

### 14.10 🟢 No lag compensation on hitscan

Covered in §4.10. The shooter aims at a target rendered 100 ms in the past, and the server
resolves against present-tick positions after 0–133 ms of input buffering. **You must lead
your shots by roughly 150–250 ms of target movement.** At 8 u/s that's 1.2–2.0 units — more
than a player's width.

This is by far the biggest *feel* problem after §14.1, and the fix is well-defined: keep a
ring buffer of historical player AABBs on the server, and in `Pistol::use` raycast against
the positions from the shooter's view-time rather than the current tick.

### 14.11 🟢 `NetworkClient.cpp:102` uses `&` instead of `&&`

```cpp
if (earlier.recievedTime <= renderTime & renderTime <= later.recievedTime)
```
Produces the correct result (bools promote to 0/1) but defeats short-circuiting. A typo.

### 14.12 🟢 Snapshots are not checked for ordering

`poll()` accepts any incoming snapshot as `latestSnapshot` without comparing `snap.tick`.
An out-of-order UDP delivery would briefly rewind authority. Trivial to guard; hasn't bitten
because localhost doesn't reorder.

### 14.13 🟢 No protocol versioning or serialisation

Raw `memcpy` of structs. Works only between identically-compiled binaries on the same
architecture. A version byte in `WelcomeMessage` would at least let you detect a mismatch
instead of silently interpreting garbage.

### 14.15 Smaller code-hygiene notes

- **`Utils.h` includes nothing** but uses `AABB`, `std::vector`, `FLT_MAX`. Compiles by luck
  of include ordering.
- **`Primitives.h` defines a non-inline global** — link error if included twice.
- **`getPlayerAABB` is duplicated in three places** (`Simulation.cpp:238`, `:307`,
  `Pistol.cpp:29-31`). Hoist it into `Simulation.h`.
- **`Pistol::tickInternal` is `private virtual` without `override`** (`Pistol.h:12`) —
  works via base-pointer dispatch, but unconventional and unchecked.
- **`UIRenderer::drawFireRect`'s 6th parameter is named `pixelSize` in the header and `id` in
  the definition** — the definition is right.
- **No destructors release GL resources** (`Mesh` VAO/VBO, `Shader` programs,
  `Texture` handles). Fine for process-lifetime objects, but `PlayingState` is `delete`d on
  transition — **so every menu→match cycle leaks 3 meshes, 5 textures, 4 shader programs and
  2 VAOs.** This will matter as soon as §14.9 gives you a way back to the menu.
- **`Level::loadLevel` fails silently** on a missing file, returning an empty level.
- **`Item*`/`WorldEntity*` are raw owning pointers.** `std::unique_ptr` would remove several
  manual `delete` sites and the leak-on-shutdown.
- **`rand()` without `srand()`** in `RoundItems.cpp` — deterministic across runs.
- **`enet_deinitialize()` is not called on the client exit path.**
- **`glGetUniformLocation` is called per-draw** everywhere. Cache in `Shader` when object
  counts grow.
